# Coverage in detail

## Collecting it

- A VSTest project needs no package, install or repo change, since `Microsoft.NET.Test.Sdk` brings Microsoft's coverage collector. On Microsoft.Testing.Platform, TUnit and MSTest's `MSTest` package bring the coverage extension; other test frameworks there need the `Microsoft.Testing.Extensions.CodeCoverage` package added to the test project.
- `uncovered.cs` also reads coverlet's reports (`--collect "XPlat Code Coverage"`), whose file names are relative to the report's source folders.
- The report covers the assemblies the tests load that have symbols: the projects under test, the other projects they load, and any package that ships symbols. It counts only what this run executes, so a `--filter` that skips slow tests also loses the lines only they run.

## What uncovered.cs prints

- **Given file names**, separated by spaces or commas: each file's lines run out of the total, its lines not run, its branches partly taken, and its members in source order. A name matches whole trailing segments of a path, ignoring case, so `Calc.cs` and `Lib/Calc.cs` match `src/Lib/Calc.cs`, but a path to a file in the report, relative to the current folder or absolute, names just that file. A name with no extension is tried as a `.cs` file too, and a name no file matches is tried as a type in the report, such as `SeedString` or `GenInt.Range`. A file named twice is shown once. Each member shows:
  - its uses: how often its name appears as a whole word in the other C# files git lists in the repo, comments and strings included, outside test code (see the last bullet). It goes by name, so it's a rough guide: a common name, such as `Create`, `Add` or `Count`, includes every other member with that name, the BCL's too, and a constructor counts every use of its type's name. Uses in Razor or XAML files don't count. An indexer or operator has no name to count, so find its uses by reading. When git can't run, the list says why and leaves the uses out;
  - the first and last of its lines, from the first overload to the last for overloads, and its lines not run, or "never run";
  - with `--callers`, its uses outside tests and in them: a count, and up to four uses, one per file, each with its line joined to the lines its brackets run on to, so the arguments show. It goes by name too, so it takes a name after a dot (`pcg.Next(...)`) or a bare one assigned to, as in an object initializer, and leaves out comments, strings, using directives and generated files (`*.g.cs`). A constructor's uses are `new` and its type's name, which misses a target-typed `new(...)`. When some uses are written after the type (`PCG.Parse(...)`), it lists only those, and for a member named like a BCL member, such as `Count`, that never is, it says to find its uses with find-references. A common name can still list another type's member, so read each line before relying on it.

  A member is a method, property, event, constructor, indexer or operator. Its lambdas, local functions, iterators and async state machines count as its own lines, and their branches add to its lines' branches. Field initializers count as the constructor's, and a static constructor shares the constructor's row. Overloads share one row, and so does an explicit interface implementation with its member. A member of a nested type is named with enough outer types to tell it apart in its file, such as `GenInt.Range.Generate`, whichever collector wrote the report. A generic type and a non-generic one of the same name, such as `Gen<T>` and `Gen`, share rows.

  `--sweep <file>` lists the uses as `--callers` does, and starts the sweep's table in that file. It won't overwrite a file that's there, so a second run can't wipe out a table being filled in. With `--callers` or `--sweep`, it warns when a test file that uses the named files' members changed after the report was written, or after the oldest of several, since a test written since then would run lines the report shows as not run.
- **Given none:** the files with the most lines not run (`--top`, default 20) in the projects under test, then totals by project. It takes the projects under test from the test project file's own `<ProjectReference>` items, or, when those are written with MSBuild properties or the report leaves the test project out, from the reported projects that no other reported project references. Other projects the tests load have their own tests, so it only totals them (`--all` ranks them too). Last, it names the projects with no test project of their own, meaning no test project in the repo named after them (`MyLib.Tests`, `MyLibTests`, `MyLib.Specs`) and none that references them alone. That's the best place for new tests, since properties there add coverage as well as finding bugs. It can't tell whether a project suits tests, so check it isn't mostly configuration.
- **Given `--since main`** (or any ref): the lines changed since the merge base, uncommitted and untracked files included, in the named files if any. It takes file names and partial paths, not type names, and says so for a name that matches no changed file. For each changed file it prints how many changed lines of code ran, the changed lines no test ran, the changed lines that aren't code, such as a const, a signature or the lines either side of a deletion, and the members the changes are in, a change belonging to the members on the next line of code, or to none above the file's first. The report has to come from the same tree as the diff, so collect coverage after the last edit. A file counts as test code by its project, so a production file named like a test still counts. It diffs the repo the current folder is in, when that holds the report's sources. Changed files in projects these tests don't load are counted by project: run those projects' tests for their coverage.
- It drops the files that don't exist on this machine, such as those of a package built elsewhere, and stops with an error when none of the report's files are here.
- **Test code** is told by project, as `dotnet test` tells a test project: by `IsTestProject` and `IsTestingPlatformApplication`, which the Microsoft.NET.Test.Sdk, Microsoft.Testing.Platform.MSBuild and TUnit.Engine packages set when they're restored. So a project is a test project when its `obj/project.assets.json` has one of those packages, unless its project file sets `IsTestProject` false. A test helper has test packages it opts out of, a test framework such as NUnit but no test platform, or a name such as `MyLib.TestUtilities`, and a benchmark project has BenchmarkDotNet. Both count as test code. A project that hasn't been restored, or keeps its restore output outside `obj`, goes by its name, so `MyLib.Tests`, `MyLibTests` and `MyLib.UnitTests` are test projects. A file belongs to the nearest project above it.

## Blind spots

- Coverage counts what ran, not what was checked: a line a test runs without asserting anything counts as covered. That's what the mutants are for.
- A branch counts as taken when the compiled code took it, which doesn't show that each operand of an `&&` or `||` decided the result: in one run a line had every branch taken, yet dropping an operand of its condition survived. The mutants that drop an operand show those.
- It only counts what this test project runs. Code tested from another project's tests shows as not run, and a file no test loads isn't in the report at all.
- For code that config drives, such as templates, formats or schemas, read the real configs too, read-only, and only with the user's agreement where they're in production, such as in a database or a cache. Coverage shows what the tests skip, not what production uses, so list the options and shapes the configs use and check each one has a test. One report showed two formats never ran, and only the production config showed that 7 expressions use them.
- Check `git branch --show-current` before saying a recent change is untested, because the user's checkout can move during a session.
